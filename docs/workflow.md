# SheetOps workflow: traceability

This document maps the n8n workflow (`workflow/sheetops.workflow.json`,
generated by `workflow/build.js`) to the rules it implements and the evidence
for each. It adds no rules of its own. The specification is
[data-contract.md](data-contract.md) (version 2.4) and
[requirements.md](requirements.md).

Evidence columns:
- **Offline**: `npm test` (the simulator runs the real workflow JSON against
  the fake Google);
- **Replay**: `npm run verify:n8n` (the real n8n 2.41.7 engine, with HTTP
  nodes replaced by recorded responses);
- **Live**: the tests in [setup.md](setup.md) §5, which have **not run yet**.

passes data between the core and the HTTP nodes. `workflow.test.js` checks
that every core-carrying node embeds the current core.

## Run states (Run Log)

```
               (no row) ── IDLE, WAIT, REFUSED: nothing written
                    │
     ┌──────────────┴──────────────┐
     ▼                             ▼
  STARTED ─ commit marker ─▶ SUCCESS | SUCCESS_WITH_EXCEPTIONS | REJECTED_FILE | HALTED_REVIEW
     │                                      (inside the atomic publish)
     ├── definitive failure, row verified ─▶ FAILED
     └── a later publish, row verified ────▶ INTERRUPTED   (superseded, not "failed")
                                           BLOCKED          (appended as final)
```

A `STARTED` row 15 minutes or older is an **unresolved publication**. By
default it blocks scheduled runs until a person reprocesses it explicitly
(contract §2; setup.md, "An unresolved publication").

## Retry and idempotency

| Call | Retried? | Why |
|---|---|---|
| Reads: listing, Run Log, download, metadata, tabs, final Review check, run row | 3 tries, 5 s apart | A read has no side effects |
| Append STARTED, append BLOCKED | Never | An append is not idempotent: a retry could add a second row |
| Publish | Never | A retry after a lost response could apply twice. Recovery is a new, version-checked plan, never a resend |
| Write FAILED row | 3 tries | It rewrites the same values into the same verified row |

## Authentication and permissions

- **Credential:** one Google service account, stored only in n8n's credential
  store as `SheetOps Google service account`. Scopes:
  `https://www.googleapis.com/auth/spreadsheets` and
  `https://www.googleapis.com/auth/drive.readonly`.
- **Sharing:** the spreadsheet is shared with it as Editor, and the inbox
  folder as Viewer. SheetOps never changes source files. One spreadsheet
  holds all five output tabs; there is no separate destination spreadsheet.
- **Export:** the workflow export references the credential by name only,
  with no ID and no secret. `workflow.test.js` scans the export for key and
  token patterns.

## Rollback

- **No automatic undo.** SheetOps writes only to its one spreadsheet. The
  publish is all or nothing, so a failed run leaves no partial state to
  undo.
- **Undoing a run that did publish:** restore an earlier version of the
  spreadsheet with **File → Version history** in Google Sheets. Before
  restoring:
  - make sure Run Log shows no `STARTED` row (no unresolved publication);
  - expect the restore to bring back an older `_sheetops_version` tab ID. A
    publish that is still in flight from before the restored point could
    then apply. This is why the first condition matters.
- **After a restore:** the batches whose Run Log rows disappeared are
  processed again on the next runs. IDs already present are filtered out, so
  this adds no duplicate rows.
- **The workflow itself:** re-import an earlier `workflow/sheetops.workflow.json`
  from Git. The core and workflow are generated together, so use the pair
  from the same commit.
